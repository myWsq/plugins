# 接入目标市场

在插件所属项目中准备交付，依据目标市场的流程完成收录或更新。此 Skill 提供通用流程，
不预设市场地址、维护仓库、凭据名称或发版命令。

## 确定目标与契约

优先使用本次用户明确指定的目标；其次读取当前项目或已加载个人配置中明确记录的市场
设置，例如适用的 AGENTS.md 中的市场地址、维护仓库和接入文档链接。
当前项目的 Git remote 用于识别插件来源，不能据此推断目标市场；Skill 的分发市场和
安装缓存目录也不是默认目标。没有目标或有多个无法区分的目标时，询问要接入哪个市场，
同时可以继续盘点本地插件。

从用户给出的契约地址，或目标市场 README/贡献指南指向的文档中获取接入要求。
契约可以是可访问的 URL 或用户指定的本地文件。若已定位维护工作区，读取其适用的
AGENTS.md。不要猜测固定的文档路径、descriptor schema、仓库分支或 CI workflow。
无法读取私有契约时，说明访问缺口并完成不依赖它的本地检查，不把其他市场的规则当成替代。

确认目标使用哪种接入方式：原生 marketplace 索引引用、收集已构建插件目录，或契约明确
支持的其他交付方式。区分可编辑的维护仓库与生成的市场产物仓库；只在规定的源头登记。
记录本次依据的契约位置，避免复制维护另一套规则。

## 准备插件交付

查看当前项目的约定、Git remote、现有插件目录和构建方式。优先复用现有可安装目录；
缺少时按目标契约选择位置，避免把整个业务仓库当作插件交付。

按契约检查 manifest、版本、许可证、组件和资源引用。尊重项目已有命名与许可证；不要
为无许可证的私有代码自行选择公开许可证。区分 Claude Code 原生格式和目标市场附加的
必需字段，不把某个 builder 的限制推广成所有市场的规则。

若目标收集已构建目录，在来源项目中完成必要的构建，并确保运行所需文件都在交付范围内；
不要假定市场会执行上游构建脚本。若目标直接引用 Git 子目录，则确认该目录可被独立安装。
检查路径边界，说明实际运行时外部依赖，按契约处理符号链接、子模块和大文件。

私有来源不代表产物私有。根据目标采用的引用或复制方式，明确发布范围及安装者所需权限；
对于复制到公开市场的方式，选中目录会公开。沿用用户已明确的发布意图，仅在可见性仍不
明确且影响交付范围时询问，不自行改变仓库可见性。

## 版本与认证

按目标契约提供版本、ref 或不可变 commit SHA；需要锁定 Git 内容时，确认所引用提交包含
最终交付文件、文件已跟踪且提交可从登记的 remote 获取。不要用包含未提交修改的工作树
冒充该 SHA 的交付状态，也不要把未推送提交或示例值登记为已经可获取的来源。

更新已有插件时，对照已登记来源和当前发布版本，遵守目标市场的版本规则；不能仅移动 tag
就声称用户会收到更新。元数据的权威来源及是否需要在索引中重复填写，由目标契约决定。

私有仓库采用目标支持的认证机制和实际要求的权限。凭据留在用户或 CI 的秘密存储中；
不把秘密值放进插件、来源 URL、接入配置或 PR。不要猜测 secret 名称或默认要求访问 Skill
作者的仓库。仅在真实验证成功后报告来源可读取。

## 登记、验证与交付

依据契约修改目标维护仓库的索引或来源配置，检查名称冲突，不覆盖无关插件。
按目标文档执行构建、版本门禁和安装检查，并分别报告实际完成的验证。若目标采用生成式
市场，不直接修改生成仓库；若索引本身就是权威源码，则按其贡献流程更新索引。

只有来源项目可用时，完成交付准备，提供维护者可采用的配置或补丁，并明确尚缺的远程
访问、真实提交或登记步骤。不要为完成接入而给用户赋予市场管理员角色。

提交、推送、PR 和发版按本次用户意图及已有权限继续。用户请求发布且目标有明确的发版
入口时，可按该入口执行并跟踪结果；安装此 Skill 本身不代表拥有市场发版权限。
没有发版权限时按目标的贡献流程提交更新请求，不绕过审核。仅询问接入办法时，解释要求
和下一步即可，不自动修改项目。

结束时报告目标市场、交付目录、插件名称/版本、来源及锁定修订、登记位置、验证结果和
尚未完成的步骤。区分“交付已准备”“请求已提交”“市场已收录”和“版本已发布”。
